# Internationalization (i18n)

The UI ships in Japanese and English and can switch at runtime. This document
describes how the dictionary works, how generated negotiation text stays in
sync, and what is intentionally *not* translated.

## Locale resolution

`src/lib/i18n/server.ts` decides the locale for every request:

1. the `bargain_locale` cookie (`ja` or `en`);
2. the `Accept-Language` header;
3. the default, **`ja`**.

`app/layout.tsx` reads that locale and renders `<html lang>` plus the page
metadata with it, then hands it to `I18nProvider` so the client starts on the
same value (no flash of the wrong language).

Switching the language in the header calls `setLocale`, which

- updates the client context,
- writes the cookie (`path=/`, 1 year, `samesite=lax`), and
- calls `router.refresh()` so server components and server-rendered text follow.

## Dictionaries

| File | Purpose |
|---|---|
| `src/lib/i18n/dictionaries/ja.ts` | Source of truth. Every key is declared here. |
| `src/lib/i18n/dictionaries/en.ts` | English. Typed as `Record<keyof typeof ja, string>`, so a missing key is a compile error. |

Keys are flat and dot-namespaced (`market.itemCount`, `offer.message.acceptBuyer`).
Namespaces in use: `common.`, `app.`, `error.`, `meta.`, `locale.`, `category.`,
`enum.`, `nav.`, `mega.`, `market.`, `product.`, `detail.`, `offer.`, `terms.`,
`role.`, `live.`, `dashboard.`, `seller.`, `deal.`, `contract.`, `approval.`,
`demo.`, `api.`, `negotiation.error.`, `reason.`.

### Placeholders

`translate` supports `{name}` and `{name,format}`:

| Placeholder | Renders |
|---|---|
| `{count}` | the raw value |
| `{count,number}` | locale-grouped number (`1,234`) |
| `{price,currency}` | `¥` plus a grouped number (`¥57,500`) |
| `{value,percent}` | `value%` |

Both locales must use the same placeholders for a key; the i18n test fails if
they drift.

### Plurals

Declare a base key plus `_one` / `_other` variants:

```ts
'market.itemCount': '{count,number} items',
'market.itemCount.one': '{count,number} item',
'market.itemCount.other': '{count,number} items',
```

`t('market.itemCount', { count: 1 })` resolves to the `.one` variant when it
exists, and to the base key otherwise. Japanese keeps identical text in both
variants.

### Adding a string

1. Add the key to `ja.ts` with the Japanese text.
2. Add the same key to `en.ts` (`tsc` lists it as missing until you do).
3. Use it: `const { t } = useI18n(); ... t('your.key', { count })`.

## Generated content

Negotiation records are written by the server, so they store **both** the
rendered string and a structured `{ key, params }`:

```ts
interface LocalizedMessage {
  key: TranslationKey;
  params?: TranslationParams;
}
```

| Record | Rendered | Structured |
|---|---|---|
| Public offer message | `messageText` | `messageTemplate` |
| Agent reasoning (heuristic/demo) | `reasoning.summary`, `factors` | `summaryTemplate`, `factorTemplates` |
| Guardrail / policy corrections | `decision.guardrailCorrection` | `decision.guardrailCorrectionTemplates` |
| Approval reason | `decision.approvalReason` | `decision.approvalReasonTemplate` |
| Contract clause | `clause.title`, `clause.body` | `clause.titleKey`, `bodyKey`, `params` |
| Approval task title | `task.title` | resolved via `approvalTitleKey` |
| Sender label | `offer.senderName` | `offer.senderKey` |

The UI prefers the structured form (`src/lib/i18n/content.ts`), so switching
language re-renders history instead of leaving old text behind. Records written
before i18n only carry the rendered string and fall back to it.

A message typed by a human is **never** re-rendered: it is shown exactly as
written.

### Session language

`NegotiationSession.locale` records the language a negotiation started in
(`POST /api/negotiations` reads it from the request). The LLM planner prompt is
built in that language, so agent reasoning is written in English for English
sessions.

### API errors

Routes resolve the request locale and return a translated message:

```ts
const locale = await getRequestLocale();
return NextResponse.json({ error: code, message: apiErrorMessage(locale, code) });
```

- `apiErrorMessage` (`src/lib/i18n/api.ts`) maps route-level codes.
- `publicError(error, locale)` / `errorMessageFor(code, locale)` map
  negotiation/safety codes.
- `getRequestLocale()` returns the default outside a request scope, so unit
  tests and scripts keep working.

## What is intentionally not translated

| Surface | Why |
|---|---|
| Catalog content (titles, descriptions, seller names, category paths) | It is marketplace data, like real listings on a Japanese marketplace. |
| LLM-generated reasoning | Written once in the session language; re-translating would mean re-running the model. |
| Counterparty-entered terms (`paymentTerms`, `warranty`) | Contract clauses explicitly state these are unverified counterparty text. App-seeded defaults (`即時決済`, `商品説明に準拠`) *are* mapped back to keys by `termValues.ts`. |
| Operator-only audit payloads | Machine-readable records, not UI copy. |

## Verification

- `npm run typecheck` — `en` must cover every `ja` key.
- `npm test` — `test/unit/i18n.test.ts` checks key parity, placeholder parity,
  empty strings, interpolation, plurals, currency formatting, unknown keys and
  `Accept-Language` handling.
- `npm run lint` — no hard-coded UI strings should reappear.

## Adding a third language

1. Add the tag to `LOCALES` and the label maps in `src/lib/i18n/config.ts`.
2. Copy `dictionaries/en.ts` to `dictionaries/<tag>.ts` and translate the values.
3. Register it in `DICTIONARIES` (`dictionary.ts`).
4. Add the language to the switcher (it maps over `LOCALES` automatically).
5. `npm run typecheck && npm test`.
